# HorizonDBとFlexible Serverの比較測定

Azure東日本に専用環境を作成し、HammerDB 6.1のTPROC-Cで比較する。既存のDBやVMは使用しない。

このリポジトリには再現用コードとオフラインテストだけを含める。測定結果、プレゼンテーション、実行履歴、個別環境の識別子、資格情報は公開しない。実行によって生成される`results/`もGitの追跡対象外とする。

## 実行前の準備

実際のAzure環境の作成・再開には、macOSのKeychain、Python 3、Azure CLI、`ssh-keygen`が必要となる。ローカルPythonに追加のpipパッケージは不要。テストには`tclsh`も必要で、テストだけならLinuxでも実行できる。

```sh
git clone https://github.com/rioriost/horizon_bench.git
cd horizon_bench
az login
export AZURE_SUBSCRIPTION_ID="$(az account show --query id -o tsv)"
az account set --subscription "$AZURE_SUBSCRIPTION_ID"
az horizondb --help
python3 -m unittest -q
```

使用するサブスクリプションが異なる場合は、`AZURE_SUBSCRIPTION_ID`に対象のUUIDを明示する。未設定・不正な形式では、結果ディレクトリの作成やAzure操作を開始する前に停止する。再開・削除でも元の実行と同じサブスクリプションを指定する。

`az horizondb --help`が利用できない場合は、HorizonDBを利用できるAzure CLIとサブスクリプションを準備する。HorizonDBの利用資格、Japan Eastでの提供状況、VM・DBのクォータ、リソース作成とロール割り当ての権限が必要になる。CLI拡張機能やサービスの提供状況は利用時点の公式ドキュメントで確認する。オフラインテストではAzureログインもDB資格情報も使わない。

クライアントVMにはUbuntu 24.04を使い、`setup.sh`でPython 3・psycopg2、PostgreSQL 17クライアント・pgbench、HammerDB 6.1などを導入する。HammerDBの配布物はSHA-256を検証する。初期導入にはVMからUbuntu・PostgreSQL・GitHubの配布先への通信が必要となる。

## 同じデータ量と負荷で測る

両サービスとも、PostgreSQL 17、8 vCPU・64 GiBのプライマリと読み取りレプリカを1台ずつ使う。HorizonDBの`--replica-count 2`はプライマリを含む。Flexible Serverは`Standard_E8ds_v5`、Premium SSD v2の2 TiB、12,000 IOPS、280 MB/sを指定する。1 TiBのデータに索引・WALなどの余裕を持たせるため、ディスク容量は2 TiBとした。ストレージの内部構造とCPU世代は一致しないため、サービス構成としての比較になる。

負荷生成には`Standard_F32as_v6`を2台使用する。通常は各サービスに1台を割り当て、ピーク付近では同じDBに2台から接続する追加測定も行う。CPU全体だけでなく、最も忙しいコア、空きメモリ、通信量も記録する。2台測定は1回の確認であり、クライアントの限界を厳密に証明するものではない。

10 warehouseの実測容量から、表と索引の合計が約50 GiB、250 GiB、1 TiBになる共通warehouse数を決める。構築用ユーザー数はwarehouse数以下に抑える。校正用データで1ユーザーの試走を済ませてから、大容量の構築に進む。実測容量が目標の±10%を外れた場合は停止する。次の容量段階へ進むときだけ専用の`tprocc`データベースを作り直し、中断後の再開では完成済みのデータを使う。

TPROC-Cの5種類のトランザクション混合は変更しない。全warehouseを対象にし、小・中では1・8・16・32・64・128・256ユーザー、大では16・64・256ユーザーで測る。各条件はウォームアップ2分・測定5分を3回繰り返し、測定順を交互に反転する。HammerDB 6.1は監視用VUを自動で1個追加するため、`vuset vu`には負荷生成ユーザー数だけを渡す。起動間隔は0にし、256ユーザーでもウォームアップ中に起動を済ませる。

各VUは通知用・SQLite用・PostgreSQL用のファイルを開く。Azureの実行環境から引き継ぐ1,024ファイルの上限では256ユーザーを起動できないため、HammerDBの起動前にワーカープロセスの上限を最低65,536へ引き上げる。既存の上限がそれ以上なら変更しない。OSが許す最大値も65,536未満の場合は、負荷をかけずにエラーで停止する。適用した値は結果にも保存する。

`vurun`は時間制限で戻る場合があるため、VU全体の完了を確認してから結果を取得・破棄する。追加の完了待ちは最大10分とし、終了しなければ失敗として記録する。出力に記録された実ユーザー数、監視用を含む全VUの成功通知、5種類のトランザクションの応答時間が揃わない結果は採用しない。VUの失敗や計測データの収集漏れが記録された結果も除外する。NOPM、TPM、トランザクション別の応答時間、DB統計、データ増加量、クライアントの使用率を保存する。応答時間はHammerDB標準のウォームアップを含む集計で、クライアント使用率は測定5分の範囲に絞る。公式監査済みTPC-Cではないため、結果をtpmCとは表記しない。

2台からの測定でもNOPMはDB全体のカウンターに由来する。両クライアントの値を足さず、1台目の監視結果を採用する。データは反復の間に増加するため、更新前後の容量も結果に残す。ウォームキャッシュの測定であり、コールドキャッシュを保証するものではない。

250 GiBでは補助試験として、同じcustomer表にpgbenchで読み取りと更新を同時実行する。提示する負荷は合計1,000トランザクション/秒で、読み取り:更新を80:20と50:50に分ける。総接続数20・80・160で、読み取り先をプライマリ／レプリカに切り替える。達成TPS、失敗・スキップ数、1%標本による読み取り／更新別p95・p99、レプリカで更新が見えるまでの時間を記録する。指定比率は投入レートの比率であり、失敗やスキップがあれば実際の完了比率とは一致しない。

## 中断した環境を残して再開する

エラー、期限切れ、Ctrl+C、SIGTERMでは、DB・ディスク・実行記録を削除しない。ローカル側で中断を検知した場合は、所有確認のうえでクライアントVMを割り当て解除する。停止に失敗した場合も、そのエラーを記録して環境を残す。完走して結果を保存できた場合と、`--cleanup`を指定した場合だけ、専用リソースグループを削除して消えたことまで確認する。

Run Commandの状態を読むAzure REST GETがDNSの名前解決で失敗した場合は、2・4・8・16・30秒の待機を挟み、初回を含め最大6回試す。待機と呼び出しには、元の実行期限と1操作あたり1時間の上限を適用する。DNS以外の失敗や、作成・更新・起動・停止・削除の操作は自動で再試行しない。外部から停止されたVMを自動起動することもない。

実行にはmacOS、Python 3、Azure CLIへのログイン、このサブスクリプションへのリソース作成・ロール割り当て権限が必要となる。DBパスワードはmacOSのKeychainに保存し、読み戻せることを確認してからデプロイする。パスワードをKeychain用コマンドの引数に載せず、OSのAPIへ直接渡す。再開には同じMacのKeychain項目と`results/<run_id>/`の両方が必要になる。ローカルの回帰確認には`tclsh`も使う。

```sh
python3 -m unittest -q
# 新規実行。run_idはresults/<run_id>/state.jsonにも記録される。
python3 infra.py run_benchmark.py

# 稼働中の環境に再接続する。停止済みのVMは自動起動しない。
python3 infra.py --resume RUN_ID

# 外部停止の意図を確認し、VMの起動を明示的に許可して再開する。
python3 infra.py --resume RUN_ID --start-clients

# 実行期限を過ぎた場合。費用を確認してから、停止期限を16時間延長する。
python3 infra.py --resume RUN_ID --start-clients --extend-hours 16

# 保存した結果を残し、専用のAzure環境とKeychain項目を削除する。
python3 infra.py --cleanup RUN_ID
```

再開時にはサブスクリプション、グループ名、所有タグ、リソースの構成を照合し、作成済みのリソースを再利用する。Azureが作成を受け付けた直後にローカル処理が途切れた場合も、実物の有無と作成状態を確認してから残りを進める。作成完了を記録したリソースやグループが消えていれば、黙って作り直さず停止する。同じ実行の再開と削除を同時に行うことも禁止する。

`progress.json`には、構築・測定ごとの固定キー、VM、入力条件、ジョブID、回収状態を、実行を依頼する前に保存する。再開時は実行中のRun Commandに再接続し、終了済みなら保存結果を使う。元のコマンドがなくてもVM上の結果ファイルから回収できる。VM側でも同じジョブの結果を再利用し、親プロセスだけが終了してHammerDBやpgbenchが残った場合は、子プロセスに引き継いだロックで二重起動を防ぐ。

構築完了時にはDB内にも実行ID・データセットID・warehouse数・構築結果を記録する。ローカルのチェックポイントだけを信用せず、現在のDBと照合してから負荷をかける。校正や小容量段階が終わっていれば、大容量段階の再開時に戻って構築し直すことはない。ただし、HammerDBのスキーマ構築そのものは途中から続けられないため、**未完了の構築だけは、そのサービスの当該段階のDBを作り直す**。もう片方の完成済みDBやインフラは残す。

完了済みの測定は繰り返さず、CSVは保存した結果から重複なく再生成する。2台同時測定は元の組み合わせで両方の結果が揃った場合だけ採用する。片方が未完了なら、旧ジョブが停止済みであることを確認して、2台とも新しい開始時刻で測り直す。中断中や不採用試行でも更新されたデータは巻き戻さない。チェックポイントの形式、負荷生成コード、入力条件が変わった場合は、異なる条件の結果を混ぜずに停止する。

新規実行では15時間を実行処理に、残り1時間を停止・後処理に割り当てる。1台目のVMにも16時間後の停止タイマーを設定するが、このタイマーはDBやディスクを削除しない。2台目のVMを停止してから1台目を停止する。タイマーのマネージドIDにはグループの参照権限と各VMの操作権限だけを与え、グループを削除する権限は与えない。実行期限は再開するたびに自動延長せず、延長には`--extend-hours`を要求する。

VMの割り当て解除中はVM内のタイマーも動作しない。組織ポリシーを変更したり、外部停止に対抗してVMを自動で起動し直したりはしない。削除済みの環境をこの再開機能で復元することはできない。

## 保存中もDBとストレージの課金は続く

クライアントVMを割り当て解除しても、DB、ディスク、パブリックIPなどの費用は残る。中断時の全削除をやめたため、環境全体の自動削除期限は設けていない。使わなくなった実行は`--cleanup RUN_ID`で削除する。

実行前に、利用先リージョンのDB・VM・ストレージの単価と費用を確認する。構築時間や中断中の保存費用も発生するため、予算内での完了を保証しない。Azureの予算アラートも課金停止にはならない。実測した構築速度から期限内に残りの作業を完了できないと判断した段階は、理由を記録して一時停止する。未実施を測定済みとして扱わない。

## 結果と接続情報の扱い

`results/<run_id>/`に状態、再開用の記録、Azure構成、各測定のJSON、TPROC-CのCSVを保存する。状態・結果ファイルは一時ファイルへの書き込みと同期を済ませてから置き換える。パスワードはこれらのファイルに書かず、VMへはRun Commandの保護パラメーターとして渡す。環境の削除を確認してからKeychain項目を削除する。VMのSSH受信ルールは開けない。SQL接続は証明書とホスト名を検証する。

測定ログは全体を保存する。大量に繰り返されるデータ構築の進捗行だけは先頭50行・末尾50行に絞り、省略行数と元ログのハッシュを明記する。CPUなどは測定中の標本から計算した集計値を保存する。完了した構築の全進捗ログはVM上に残すが、専用環境の削除とともに消える。

Azure管理メトリクスは、取得する指標の組み合わせごとに、APIが共通して対応する最も細かい間隔で保存する。すべての指標が1分間隔に対応するとは限らない。応答に含まれる取得間隔を確認し、各測定のクライアント使用率の標本集計と区別して扱う。

結果は圧縮してAzure管理API経由で回収し、ハッシュを照合する。通常は1回の応答に収め、大きい結果だけを分割する。Run Commandは終了状態を記録してから削除し、削除完了を待って次へ進む。回収途中で中断してもVM上の結果は残る。まだ動作中のコマンドは、中断時の後処理で削除しない。再開時には放置された終了済みコマンドも整理し、VMあたり25件の上限に達しないようにする。DBを作成する前に、両VMで約3.6 KBの結果回収とコマンド削除を試す。Blob Storageの公開アクセスを無効にする組織ポリシーは変更せず、転送用ストレージも作成しない。
